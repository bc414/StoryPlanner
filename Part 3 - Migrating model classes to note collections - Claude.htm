Apr 21 Claude responded: The Three Fundamental Problems Dissected architectural tensions between EF Core, WPF, and design principles Dissected architectural tensions between EF Core, WPF, and design principles The Three Fundamental Problems Before discussing EF Core or WPF specifically, there are three problems that exist at the pure design level. The technology choices either make them easier or harder, but don't create or eliminate them. ------------------------------------------------------------------------ Problem 1 — Ownership Resolution A |Note| must belong to exactly one owner. That ownership must be resolvable in both directions — from the owner to its notes, and from a note back to its owner. Every design decision downstream flows from how you resolve this. The wide nullable FK approach you started with is the simplest schema but produces an incoherent model — |Note| knows about every possible owner type, which means adding an 11th ownable entity requires a schema change to |Note|. It also makes ownership validation a runtime concern rather than a compile-time one. TPH inheritance solves the model incoherence cleanly. Each derived |Note| type knows exactly one owner type. Adding an 11th type means adding one new class, one new migration that adds one nullable FK column — |Note|'s base class never changes. The tradeoff is that the single |Notes| table grows wide with mostly-null FK columns, which is acceptable at your scale and is the standard EF Core TPH consequence. The alternative worth considering from scratch is *a generic ownership table* — a separate |NoteOwnership| table with a discriminator, an owner ID, and a note ID. This eliminates nullable FK columns entirely from |Notes|. But it adds a join to every note query and makes EF navigation properties significantly more awkward to configure. For a personal project this trades a manageable schema concern for a persistent query complexity burden. TPH is the better choice here. Problem 2 — The Model/ViewModel Boundary This is the most consequential design decision and it's independent of both EF Core and WPF. The question is: *what is a model's job versus a ViewModel's job?* The failure mode in your current code, which is extremely common in WPF MVVM projects, is that the models are doing ViewModel work. |ObservableObject| on |PlotPointCharacter| means the model carries change notification infrastructure. |[ObservableProperty]| on model fields means binding is wired directly to the persistence layer. This feels convenient early and becomes a source of bugs and bloat because the model's lifecycle and the ViewModel's lifecycle are different things — a model instance should survive as long as the data exists, while a ViewModel instance should survive only as long as a view is open. The clean design is a strict boundary: * *Models* are pure data containers. No MVVM toolkit dependency whatsoever. They serialize, they persist, they carry no UI awareness. * *ViewModels* wrap models and own all observable state. They are constructed from models, they push changes back to models before persistence, and they are disposed when the view closes. This boundary is not enforced by any framework — EF Core doesn't care and WPF doesn't care. It is a discipline decision. But it is the decision that determines whether your ViewModel generalization effort succeeds or accumulates new debt. Problem 3 — Change Tracking Ownership Who is responsible for knowing that a |Note| was added, modified, or deleted? This problem has three candidate owners and most projects accidentally distribute it across all three, which causes bugs. *Option A — EF Core's change tracker owns it.* You load entities into a long-lived |DbContext|, make changes directly to tracked entities, and call |SaveChanges|. This is the simplest mental model and works well for desktop apps where the context can be scoped to a session. The risk is that long- lived contexts accumulate tracked entities and memory pressure grows over time, and that accidental mutations on tracked entities persist on the next |SaveChanges|. *Option B — ViewModels own it.* ViewModels maintain a list of pending operations (added notes, modified notes, deleted notes) and a dedicated save action flushes them to a short-lived |DbContext|. This is more explicit and testable but requires you to implement the pending-operations pattern yourself. *Option C — A Unit of Work owns it.* A UoW object is opened for an editing session, collects all changes, and commits or rolls back atomically. This is the most architecturally pure option and maps well to your use case — opening an entity editor, making changes to notes and payload fields, then either saving or canceling the whole set. For a personal WPF project, Option A with a session-scoped context is pragmatic and defensible. The risk is manageable if you are disciplined about not holding the context longer than a top-level window's lifetime. ------------------------------------------------------------------------ Where EF Core Specifically Creates Friction EF Core's friction points in this design are concrete and predictable. *Navigation property loading.* EF Core does not automatically load navigation properties. |Character.Notes| is null until you either eagerly load it with |.Include()|, lazily load it (requires proxy configuration), or explicitly load it after the fact. For a collection like notes that you always want when you open an entity editor, eager loading via |.Include()| is the right call — but you must remember to include it in every query that feeds an editor ViewModel. A repository pattern with a well-defined |GetForEditing| method that always includes the right navigations is the standard mitigation. *TPH and polymorphic queries.* When you load a |Character| with |.Include(c => c.Notes)|, EF returns the collection typed as |ObservableCollection| but the instances are correctly typed derived objects at runtime — |CharacterNote| instances. This is correct behavior but requires that your ViewModel and XAML handle the base type in collections while occasionally needing to downcast. This is manageable but worth knowing in advance. *SQLite and concurrent writes.* SQLite serializes writes. For a single- user desktop app this is irrelevant, but it means your architecture should never attempt concurrent save operations. A single UI thread with synchronous saves or properly awaited async saves is sufficient. ------------------------------------------------------------------------ Where WPF Specifically Creates Friction WPF's friction is primarily in three places. *DataTemplate selection for derived types.* If your notes collection contains base |Note| references that are actually derived instances, and you want different visual treatment per derived type or per |NoteTrack|, WPF's |DataTemplateSelector| is the mechanism. It selects a template based on the runtime type of the bound object. Without it, WPF uses the most specific matching DataTemplate it can find — if you define a DataTemplate for |Note|, all derived types use it unless you define more specific ones. This needs to be designed intentionally or your generic window will not render note types differently if you ever want that. *ObservableCollection and thread affinity.* WPF's binding system requires that |ObservableCollection| mutations happen on the UI thread. If you ever load notes asynchronously (which you will want to do for perceived performance), you must marshal the collection population back to the UI thread. |BindingOperations.EnableCollectionSynchronization| is the standard mitigation. *The generic ViewModel / XAML boundary.* WPF's XAML does not support generic type arguments directly in markup. |NoteableViewModelBase| cannot be referenced directly in XAML. The standard pattern is to have the generic base class and then thin non-generic subclasses that XAML can reference by name, which is also where your entity-specific properties live. This is not a significant burden — it aligns with the thin subclass pattern already described — but it means you cannot eliminate the subclasses entirely even if the base class does all the work. ------------------------------------------------------------------------ The Cleanest From-Scratch Design Given all of the above, the architecture that minimizes long-term complexity is: *Schema layer.* TPH on |Note| with surrogate PKs on junction entities and unique constraints preserving composite integrity. |NoteTrack| is a column on |Notes|, semantically inert to the schema. *Model layer.* Plain C# classes with no MVVM toolkit dependency. Models are the source of truth for what the data is. *Repository layer.* One generic repository interface |IRepository| covering CRUD, plus entity-specific query methods where the generic pattern breaks down — primarily the |GetForEditing| methods that specify which navigations to include.
